## 已确认结论

### 3. 真机 / 仿真运行模式区分

根据 transcript，目前能确认的结论是：

- `blockly` 和 `流程图` 是两套现有入口，运行逻辑不同
- 运行目标选择必须挂在各自已有的执行按钮附近实现
- `blockly` 里原来叫“发送”的播放图标，讨论目标是改成“执行语义”，而不是让用户理解“发送”
- 至少需要提供两个勾选项：
  - 真机执行
  - 仿真运行
- 至少勾选一个才能执行
- 真机未连接时，真机项禁用
- 体验上应尽量趋同，但不能为了趋同而抽成一套全局面板

### 3.1 关于 Build

`Build` 不是当前已经完全确认的硬性前台需求。

从 transcript 看，`build` 更像一次“参考 IDE 范式”的延伸讨论，而不是已经敲定的最终交互：

- 已明确确认的是：“不要定义为发送，而是执行按钮 + 两个勾选”
- `build` 出现在后段讨论中，带有“可以参考常见 IDE”的探索性质
- 因此第一阶段不应把 `Build` 作为全局主入口直接落 UI

更稳妥的判断是：

- 底层可能仍然存在“生成可执行数据”的步骤
- 但在前台体验上，优先先把“执行目标”和“执行语义”理顺
- 是否单独暴露 `Build`，应在后续对真实操作链路再核一次后决定

### 3.2 关于全局状态

不建议继续把“真机 / 仿真”做成全局控制面板或全局运行工具栏。

可以保留的只有两类轻量能力：

- 数据层上的最小共享 schema
- 非侵入的被动状态展示

不能继续做的包括：

- 在宿主层新增一套独立执行区
- 用宿主层按钮替代子应用原有执行按钮
- 把 `blockly` 和 `流程图` 的执行动作强行抽象成同一条全局逻辑

### 3.3 趋同原则

虽然两套模式功能数量不同，但执行区的体验应尽量趋同。

建议统一的是：

- 主执行按钮的语义
- 执行目标选择的内容
- 停止动作的位置关系
- 禁用和未选择时的规则
- 运行状态文案体系

允许不同的是：

- 各自模式原有的外围功能数量
- 图标按钮或文字按钮的表现形式
- 具体执行后的内部调用链

## 推荐的第 3 项重构方向

### Blockly

以原有 `运行 / 停止` 区域为中心重构，不额外创造新面板。

建议：

- 保留原有运行入口附近的空间关系
- 在 `运行` 按钮旁增加“执行目标选择”
- 目标选择以勾选菜单展开
- `停止` 仍紧邻执行区
- 如果底层仍需要“发送 / 生成”，先作为执行前内部步骤处理，不抢占前台主位

### 流程图

以原有 `播放 / 暂停(停止)` 图标区为中心重构，不与 `blockly` 共用宿主层执行控件。

建议：

- 播放按钮仍然是主执行入口
- 播放按钮旁增加同语义的目标选择器
- 停止按钮与目标选择器保持同一相对顺序
- 非执行类图标保持原工具栏位置，不因趋同而重排整条工具栏

### 两套执行区的统一规范

建议统一成“执行簇”的概念，而不是“整条工具栏完全一致”：

- 主执行
- 目标选择
- 停止

对应规则：

- 默认仅勾选仿真
- 真机未连接时不可勾选
- 点击主执行时，按当前勾选目标执行
- 文案体系一致：
  - 真机执行
  - 仿真运行

## 4-7 项判断

### 4. 夹取物品交互优化

不要继续让用户输入“第几个物品”这种底层编号。

建议做成“结构化选择器”：

- 在动作块或参数面板旁提供矩阵 / 列表 / 区域选择
- 支持 `全部`、`前 N 个`、`范围` 等高层表达
- 通过对象索引表，把 UI 选择映射到底层 ID

这项的关键前提不是 Blockly，而是先建立一份稳定的场景对象索引。

### 5. IO 状态仿真编辑

不建议把仿真逻辑直接混进真机主流程。

更稳妥的方案是引入独立的 `simulation profile`：

- 描述某一步或某个动作触发哪些 IO 信号
- 支持触发时机、延迟、随机等待、成功 / 失败分支
- 仿真模式读取
- 真机模式完全忽略

这样业务脚本和仿真补偿逻辑可以彻底分离。

### 6. 两级用户界面设计

这本质上不是“双页面”，而是“底层编排能力”与“上层暴露模块”之间增加一层发布模型。

建议新增 `published module manifest`：

- 底层界面负责完整编排
- 开发人员选择哪些参数对外暴露
- 配置默认值、范围、步进、文案、图标和校验
- 上层界面只消费已发布模块，不再直面点位、电机和 IO 细节

### 7. 实验流程卡片化展示

不建议先于第 6 项单独落地。

卡片应代表“实验模板 / 已发布流程”，而不是底层 `flow_data` 的直接可视化。

建议卡片实体包含：

- 名称
- 描述
- 版本
- 标签
- 暴露参数摘要
- 编辑
- 删除
- 进入流程
- 直接运行

## 推荐实施顺序

### 稳妥顺序

1. 第 3 项：重构两套本地执行区
2. 第 5 项：IO 仿真 profile
3. 第 4 项：夹取物品结构化交互
4. 第 6 项：发布模块机制
5. 第 7 项：实验流程卡片

### 用户感知优先顺序

1. 第 3 项：重构两套本地执行区
2. 第 4 项：夹取物品交互优化
3. 第 5 项：IO 仿真 profile
4. 第 6 项：发布模块机制
5. 第 7 项：实验流程卡片

当前建议继续采用“稳妥顺序”。

## 第一阶段实施边界

### 本轮应做

- 清除宿主层里错误的全局执行区思路
- 在 `blockly` 和 `flow-path` 各自原有执行按钮附近重构执行目标选择
- 统一两套执行簇的语义、顺序和状态规则
- 保留宿主层仅做被动状态同步

### 本轮不做

- 把 `Build` 定成已经最终确认的前台主按钮
- 用宿主层替代子应用原生执行入口
- 深改原版 bundle 的底层执行逻辑
- 真机真实连接
- IO 仿真配置面板
- 上层实验卡片系统

## 落地原则

- transcript 已明确的内容优先于推测
- 先统一语义和顺序，再讨论是否增加新按钮
- 宿主层只做辅助，不抢子应用主入口
- 功能可以不同，执行心智必须尽量一致
